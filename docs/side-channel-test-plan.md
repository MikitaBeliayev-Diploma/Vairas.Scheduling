# План проверки побочных каналов доступности учащегося (AC-091 / US-008)

| Поле | Значение |
|---|---|
| Критерий | AC-091 (US-008); связанные AC-018–AC-023, AC-083, AC-090, AC-094–AC-096, AC-099 |
| Сервис | Vairas.Scheduling |
| Версия плана | 1.0, 2026-11-25 |
| Статус | **ОЖИДАЕТ УТВЕРЖДЕНИЯ владельцем проекта** (см. §12). План не утверждён; результаты в §10 — локальные измерения на синтетических данных. |

## 1. Цель

Перед включением межшкольной проверки доступности для реальных людей (`Scheduling:RealPersonProcessingApproved`) показать, что школа A, проверяющая доступность **своего** зачисленного учащегося, не может по наблюдаемым признакам ответа отличить «учащийся занят в другой школе» от эквивалентных собственных причин недоступности, а массовые запросы ограничены по окну, объёму и частоте с минимальным ограниченным аудитом.

Раскрытие самого факта «учащийся недоступен в момент T» — **намеренное** поведение (глобальная проверка конфликта учащегося, AC-018/AC-083). План проверяет, что сверх этого факта ничего не раскрывается, а сам факт нельзя собирать в больших объёмах.

## 2. Область

В области:

- `GET /api/v1/schools/{schoolId}/availability` (route name `findAvailableLessons`), в том числе через MCP read-preview (`find_available_lessons`);
- отказы `POST /api/v1/practical-lessons` (создание) и `POST /api/v1/practical-lessons/{id}/rescheduling` (перенос), вызванные: резервированием того же учащегося в другой школе; собственным конфликтом школы (учащийся/преподаватель/автомобиль); правилом, нарушаемым только вместе с чужими занятиями (перерыв, дневной лимит);
- предварительные просмотры `booking-previews` / `rescheduling-previews` (ConfirmedLessonActionsV1), так как они используют ту же проверку;
- лимиты: окно запроса > 31 дня, > 1 000 оцениваемых слотов, 60 запросов/мин на пару (пользователь, школа), 300 запросов/мин на школу, повторное перечисление;
- аудит, создаваемый при этих событиях.

Вне области (см. §11): генерация расписания (`PlanningService`), внутренний шлюз School (`GateService`), Gateway и сетевой уровень, производственная инфраструктура.

## 3. Модель угроз

**Нарушитель:** аутентифицированный сотрудник школы A с правом администратора (или его делегированный MCP-ассистент), действующий в пределах своих прав.

**Цель нарушителя:** узнать о другой школе B: учится ли там учащийся, когда у него занятия, их длительность, с каким преподавателем/автомобилем, и изменения этого календаря во времени.

**Возможности:** произвольные корректные запросы к перечисленным конечным точкам; повтор одного запроса; варьирование времени, длительности, окна, написания URL; измерение времени ответа; сравнение тел, длин, заголовков, кодов; чтение собственных записей операций (`GET /api/v1/scheduling-operations/{id}`).

**Вне модели:** компрометация БД, журналов или токенов; сговор со школой B; доступ к сети между сервисами.

## 4. Наблюдаемые каналы

| Канал | Что проверяется |
|---|---|
| HTTP-статус | одинаков внутри класса эквивалентности |
| Код ошибки (`code`) | одинаков; нет кода, специфичного для чужой школы |
| Тело ответа | побайтово одинаково после нормализации `correlationId` и идентификаторов, выбранных самим вызывающим (школа в `instance`, урок в пути) |
| Размер тела | сырой размер в байтах одинаков |
| Заголовки | одинаковый набор и значения, кроме `Date` и значения `X-Correlation-ID` (эхо запроса или случайный UUID); `Cache-Control: no-store`; `Retry-After` — константа `60` |
| Время ответа | статистически неразличимо (§7) |
| Побочные эффекты аудита | одинаковая запись `scheduling_operation` (Rejected, код, HTTP-статус, `{}`); доступность не пишет записей |
| Счётчики лимитов | 429 одинаков для лимита пользователя и лимита школы; лимит одной школы не влияет на другую |
| Хеш основания превью (`sourceRevisions.basis`) | не зависит от неконфликтующих чужих занятий |

## 5. Классы эквивалентности

Для слота 08:00–08:45 учащегося L школы A:

| ID | Причина недоступности | Ожидаемый ответ создания/переноса | Ожидаемый ответ доступности |
|---|---|---|---|
| E1 | занятие L в школе B, пересекается | 409 `RESOURCE_UNAVAILABLE`, отказ записан | слот отсутствует |
| E2 | занятия L в школе B 06:30–08:00 (нарушение перерыва только вместе с ними) | 409 `RESOURCE_UNAVAILABLE`, отказ записан | слот отсутствует |
| E3 | собственное занятие L (другой преподаватель/автомобиль) | 409 `RESOURCE_UNAVAILABLE`, отказ записан | слот отсутствует |
| E4 | собственный преподаватель занят | то же | то же |
| E5 | собственный автомобиль занят | то же | то же |
| E6 | автомобиль неприменим (владелец Vehicle) | 409 `RESOURCE_UNAVAILABLE` с тем же телом; запись операции **не** создаётся (отказ до резервирования) | все слоты отсутствуют (не слотовый класс) |
| D1 | L не зачислен / нет права (независимо от наличия чужих занятий) | 403 `ACCESS_DENIED`, глобальное чтение не выполняется | 403 `ACCESS_DENIED`, глобальное чтение не выполняется |
| O1 | собственные занятия школы A объясняют нарушение правила | 409 `BUSINESS_RULE_REJECTED` / превью `PREVIEW_NOT_AVAILABLE` (неизменно; только собственные данные) | слот отсутствует |
| L1/L2 | превышен лимит пользователя / школы | 429 `RATE_LIMIT_EXCEEDED`, `Retry-After: 60`, одинаковые тела | — |

E1–E5 должны быть неразличимы по всем каналам §4. E6 и O1 отличаются только данными, которые школа A уже знает (свой автомобиль, свой календарь).

## 6. Критерии приёмки

1. **Содержимое.** Внутри класса E1–E5 (и отдельно D1, L1/L2): одинаковые статус, `code`, сырая длина тела, тело после нормализации и заголовки (кроме `Date`). Нормализация заменяет только `correlationId` и идентификаторы, которые вызывающий сам указал в URL.
2. **Отсутствие лишних фактов.** Ни одно тело не содержит идентификаторов другой школы, учащегося, записи, урока, преподавателя, автомобиля или времени чужого занятия; при D1 глобальный источник резервирований не вызывается.
3. **Время.** Для пар (E1, E3) на реальном PostgreSQL: N = 200 пар после 20 прогревочных, порядок внутри пары случайный (seed 91), статистика — медиана парных разностей `d = t(E1) − t(E3)`. Порог: `|median(d)| ≤ max(0,25 · median(t(E3)); 1 мс)`. Дополнительно сообщаются p10/p90, бутстреп-95% ДИ медианы (2 000 выборок) и z-статистика знакового теста; ориентир |z| < 3. Проверяется отдельно для отказа создания и для запроса доступности.
4. **Лимиты.** Окно > 31 дня → 400 `QUERY_WINDOW_EXCEEDED`; более 1 000 слотов → 422 `QUERY_VOLUME_EXCEEDED`; ровно 31 день и ровно 1 000 слотов обслуживаются; 61-й запрос пары (пользователь, школа) за минуту и 301-й запрос школы → 429 c `Retry-After: 60`; другая школа и другой пользователь не блокируются; регистр пути, завершающий `/` и любое написание GUID школы используют тот же счётчик.
5. **Аудит.** Каждое превышение лимита (429, `QUERY_WINDOW_EXCEEDED`, `QUERY_VOLUME_EXCEEDED`, `RESULT_LIMIT_EXCEEDED` на доступности) создаёт ровно одно событие §9 и ничего больше; обычные ответы событий не создают; доступность не пишет `scheduling_operation`.

## 7. Методика измерения времени

- Уровень: прикладной сервис (`SchedulingService`) с реальными `SchedulingStore` и `ReservationAuthority` на PostgreSQL 17 (Testcontainers), ограниченные роли и RLS как в production-схеме. HTTP-уровень добавляет одинаковую сериализацию для побайтово одинаковых тел (§6.1), поэтому измеряется отдельно не был.
- Данные: E1 — 2030-02-05 08:00, E3 — 2030-02-19 08:00 (разные ISO-недели, в каждом учётном окне ровно одно занятие); свободный контроль — 2030-03-05.
- Чередование пар со случайным порядком компенсирует дрейф (прогрев кэша, рост таблицы отказов, фоновая нагрузка).
- Ограничения: одна машина, Docker Desktop, малый синтетический объём, без сети между сервисами. Это **локальное измерение, не гарантия для production**. Перед включением измерение повторяется на целевой инфраструктуре через Gateway (§10.3).

## 8. Тесты лимитов и перечисления

| Проверка | Ожидание |
|---|---|
| `to − from` = 31 дн. 45 мин | 400 `QUERY_WINDOW_EXCEEDED`, аудит |
| 1 001 слот по 14 мин | 422 `QUERY_VOLUME_EXCEEDED`, аудит |
| `durationMinutes = 0` | 400 `VALIDATION_FAILED`, без аудита лимита |
| ровно 31 день (60 мин) и ровно 1 000 слотов (30 мин) | 200 |
| 60 запросов пользователя U в школе S, затем 61-й | 200 ×60, затем 429, `Retry-After: 60`, аудит |
| тот же U в школе S′; другой пользователь в S | 200 |
| 6 пользователей × 50 в школе S, затем 7-й пользователь | 200 ×300, затем 429; другая школа — 200 |
| 429 по лимиту пользователя vs по лимиту школы | побайтово одинаковы |
| повторное перечисление разными написаниями: `/API/V1/SCHOOLS/...`, завершающий `/`, GUID в верхнем регистре и формате `N` | общий счётчик: 61-й запрос любого написания → 429 |

Повторное перечисление учащихся ограничивается теми же счётчиками: каждый запрос касается одного учащегося одной школы и не более 1 000 слотов, поэтому за минуту пара (пользователь, школа) получает не более 60 ответов, а школа — не более 300.

## 9. Ожидания по аудиту (минимальный ограниченный аудит)

Что фактически записывает код:

- **Превышение лимитов доступности** — событие журнала категории `Vairas.Scheduling.Audit`, `EventId 9101 AvailabilityLimitExceeded`, уровень Warning, поля строго: `Code`, `SchoolId` (канонический GUID из маршрута), `ActorPseudonym` (первые 16 hex SHA-256 от `"vairas-scheduling-audit/1:" + sub`), плюс область `CorrelationId`. Не записываются: учащийся, запись, преподаватель, автомобиль, филиал, окно запроса, результат, исходный `sub`, данные другой школы. *(Поправка этой версии: до неё превышение лимитов не аудитировалось.)*
- **Отказы создания/переноса** — существующая строка `scheduling_operation` школы A (RLS): `Rejected`, `OutcomeCode`, `HttpStatus`, `ResultJson = "{}"`; для E1–E5 одинакова.
- **Доступность** — строк не пишет. Общая строка HTTP-журнала содержит шаблон маршрута, статус и длительность, без параметров запроса.

Маршрутизация категории `Vairas.Scheduling.Audit` в хранилище с ограниченным доступом и срок хранения — решение при развёртывании (§12).

### 10.3 Найденные утечки и исправления

1. **Код отказа выдавал вид чужого конфликта** (AC-019/AC-083). Чужие занятия, не пересекающиеся со слотом, но нарушающие перерыв или дневной лимит вместе с ним, давали `409 BUSINESS_RULE_REJECTED` (превью — `PREVIEW_NOT_AVAILABLE`), а пересечение — `RESOURCE_UNAVAILABLE`; тело различалось и по длине (247 против 245 байт при переносе). Исправлено: `SchedulingRules.RejectionCode` повторно оценивает правила только по сессиям школы; если отказ без чужих сессий исчезает, ответ — `RESOURCE_UNAVAILABLE`. Оценка выполняется при каждом отказе, чтобы её стоимость не зависела от наличия чужих занятий. Отказы, объяснимые собственными данными школы, не изменились.
2. **Хеш основания превью зависел от чужого календаря.** `sourceRevisions.basis` хешировал все сессии учётного окна, включая занятия L в других школах; повторное превью свободного слота показывало изменения чужого календаря. Исправлено: хеш берёт только сессии школы A. Любое значимое чужое изменение заново проверяется под блокировкой записи и отклоняется как `RESOURCE_UNAVAILABLE`. Для превью без чужих сессий значение хеша не изменилось.
3. **Обход лимитов.** Разбиение выбирало конечную точку по `Path.EndsWith("/availability")` (с учётом регистра) и брало исходную строку GUID школы. Путь в другом регистре или с завершающим `/` полностью снимал лимит; каждое написание GUID открывало новый счётчик. Тест подтвердил обход на старом коде. Исправлено: конечная точка определяется по метаданным маршрута `findAvailableLessons`, школа приводится к каноническому GUID.
4. **Не было аудита превышения лимитов** — добавлено минимальное событие §9.

## 11. Остаточные риски и вне области

- Лимиты хранятся в памяти процесса; при нескольких экземплярах они умножаются. Перед масштабированием нужны общие ограничения на входе (Gateway). Фиксированное окно допускает до 2× всплеск на границе окон.
- Отдельного детектора перечисления многих учащихся нет; ограничивают счётчики §8, а псевдоним в аудите позволяет анализировать повторы позже.
- E6 (автомобиль неприменим) не создаёт строку операции, в отличие от E1–E5: отличие касается собственного автомобиля школы, не чужих данных.
- Генерация предложений (`PlanningService`) по своей природе исключает недоступные слоты; внутренний `GateService` (School) возвращает `BUSINESS_RULE_REJECTED` доверенному сервису School, а не пользователю. В этот план не входят.
- Время измерено на уровне сервиса и малом объёме данных; в production доминирует сетевой джиттер, но повторное измерение на целевой инфраструктуре обязательно.

## 12. Критерии входа и выхода

**Вход:** сборка без предупреждений; только синтетические данные; `RealPersonProcessingApproved=false`; Docker для PostgreSQL; лимиты как в README.

**Выход (для этой стадии):** все тесты категории `SideChannel` проходят в `scripts/verify.ps1`; результаты §10 записаны; план утверждён (§13).

**Выход (для включения реальных данных, вне этой стадии):** повторный прогон §6–§8 на целевой инфраструктуре end-to-end через Gateway; общие лимиты на входе; аудит направлен в хранилище с ограниченным доступом и утверждённым сроком хранения; решения AC-099 (DPIA и др.).
